01

Should you use vLLM?

You asked this directly, so here it is before the reasoning. My first instinct was wrong and an adversarial check caught it.

Short answer

Yes, vLLM can serve it — but I'd still start with ComfyUI.

“vLLM can't do diffusion” is the answer I expected to give you, and it's wrong. There is an official dgx_spark_gb10: verified profile for MiniMax H3 in the vLLM recipes repo, with exact launch flags. But verified means “it runs,” not “it's the best fit,” and on a 121 GiB box the two paths are far apart on headroom.

Recommendation

ComfyUI first, because you said you want to learn this. It shows you every stage of the pipeline as a separate node, it's where the turbo LoRAs and attention kernels actually work, it leaves you 49 GiB of slack to experiment in, and it downloads 4× less.

The precise correction

“pip install vllm can serve H3” is false. Core vLLM lists zero diffusion architectures; its MiniMax entries are MiniMaxM2ForCausalLM and MiniMaxM3SparseForCausalLM, both text LLMs. The engine that works is vLLM-Omni, a separate official vllm-project extension, needing vLLM ≥ 0.26.0 plus current vllm-omni main.

Also worth knowing: a widely-cited vLLM issue claiming vLLM is entirely broken on DGX Spark is stale — it predates the August arm64 image. You'll find it; ignore it.

02

What MiniMax H3 actually is

Every figure below came out of the repo's own config files, then survived an adversarial re-check against primary sources.

It is not a video model. It's an omni-modal model that generates video and natively synchronized stereo audio in the same denoising loop — no separate vocoder, no audio post-pass. Speech, footsteps and score come out of the same forward passes as the pixels. That single fact drives most of what follows.

The number that constrains everything

One DiT partition (61.7) + the Qwen3-VL conditioner (62.1) = 123.8 GiB in bf16. Your box has 121.7 GiB total Measured, and Xorg plus gnome-shell are already holding 873 MiB of it.

bf16 does not fit. Not “is tight” — does not fit. Quantization is mandatory here for capacity reasons, which is a completely different motivation from the speed reasons you quantize an LLM for. Hold that thought; §07 shows it buys you almost no speed at all.

Fixed 24 fps, quantized durations
Frame counts snap to 17n+5, so legal clips are 5.17 s / 8.00 s / 10.13 s / 15.08 s. Max canvas is exactly 1344×768 = 1,032,192 px. You do not get arbitrary lengths the way an LLM gives you arbitrary token counts.
No CFG, at all
The released weights are guidance-distilled. There is no guidance_scale, no negative_prompt, and exactly one forward pass per step. Every guide you read about “CFG doubles your batch” is already handled — don't go looking for the knob.
No cross-attention to text
Unlike Wan, H3 is single-stream: text conditioning, keyframe latents, audio latents and video latents are packed into one sequence and self-attended together. This is why the sequence gets so long, and why §07's attention math dominates.
~13 B of the 33 B is AdaLN
Those modulation outputs can be precomputed and cached, so inference-only deployments needn't load them — hence community “pruned” checkpoints around 20.1 B.

Why the two stacks need wildly different amounts

The natural assumption is that you need the weights either way, so the memory should be similar. It isn't — by 64 GiB — and the reasons are worth understanding because they generalize to every diffusion deployment you'll do.

First: the repo is a menu, not a bundle. Comfy-Org/MiniMax-H3 totals 438.6 GiB Measured, but its ten diffusion_models/ files are the same model at different precisions. You take one row.

Third — and this is where the 64 GiB actually goes — who quantizes what. vLLM's GB10 profile passes --quantization fp8, which is online: it reads full bf16 from disk and converts during load. The text encoder alone is 47.5 of the 64 GiB gap — a frozen LLM used as a feature extractor, carried at full precision because the DiT-only quantizer never touches it.

And peak is not the same as resident

The rest of the gap between 41 GiB resident and ~72 GB peak is activations, attention workspace, and VAE decode buffers — temporal VAE decode inflates every frame at once and is a known spike.

But the structural reason vLLM peaks higher is that it is a server. It keeps all five models warm so the second request doesn't pay the 519–543 s cold start. ComfyUI can sequence the pipeline — encode the prompt, free the text encoder, denoise, free the DiT, decode — because it's a workstation tool that accepts reload cost. That's a latency-for-memory trade baked into what each thing is, not an efficiency difference between them.

03

What “pruned” actually removes

Determined by range-requesting the safetensors headers — 57 KB out of a 61 GiB file is enough to list every tensor. Measured

Correction

An earlier draft of this briefing said pruning was “free, not lossy.” That repeated the model card's framing without checking it. It is mildly lossy, and the detail matters because it also creates a LoRA incompatibility.

Only four tensors are genuinely deleted — the time_embedder, about 20 M params. The other 13.0 B are refactored:

Header diff, fl2va_bf16 vs fl2va_pruned_bf16. 535 → 532 tensors, 33.12 B → 20.11 B params.
TensorFullPruned
blocks.N.adaln_proj.linear.weight[96768, 2688] BF16[96768, 8] F16
blocks.N.adaln_proj.linear.bias[96768] BF16[96768] F16
time_embedder.*4 tensorsremoved
adaln_t_table—[1025, 8] F32 added
all 531 others (qkv, out_proj, fc1, fc2 …)identical shape and dtype

The original path is t → time_embedder → 2688-dim → [96768×2688] → modulation. The pruned path is t → adaln_t_table[t] → 8-dim → [96768×8] → modulation. As the timestep sweeps its range the modulation output traces a curve that lies near enough in an 8-dimensional subspace, so they re-expressed the projection in that basis with a 1025-entry lookup table.

Two real approximation sources follow: the rank-8 basis is a fit, not an identity; and timesteps off the 1025-point grid must interpolate. The BF16 → F16 switch on exactly these tensors (10 mantissa bits instead of 7) is a deliberate precision increase to offset it — which tells you the authors knew it was lossy.

Why it still probably doesn't matter much

Every tensor on the content path is untouched. AdaLN never sees your latents — it emits per-timestep scale/shift/gate scalars, a smooth low-frequency control signal shared across all tokens. Error there changes how strongly block 31 modulates at step 7, not the learned features.

By contrast int8_convrot quantizes the actual matrices your latents flow through. The quantization is very likely the larger quality risk than the pruning — and nobody flinches at that one.

I also checked whether ComfyUI would detect fp8 support on sm_121 at all, since PyTorch itself warns that 12.1 is “outside supported range.” It does: the gate is props.major >= 9 and GB10 reports major 12, so --supports-fp8-compute is unnecessary. NVFP4 detection (major >= 10) passes too.

Verify this on your first run

I confirmed the flag exists and that fp8 is detected — not that ComfyUI's H3 model code actually routes through torch._scaled_mm. Test it: same seed, with and without --fast fp8_matrix_mult. If step time roughly halves you are on native fp8. If it barely moves, the model path is dequantizing, the fp8-vs-int8 distinction stops mattering, and fl2va_pruned_bf16 (37.46 GiB) becomes the better pick — you would be paying quantization error for nothing.

05

How generation actually works

What a DiT is, where the noise comes from, and why nothing in this system contains a video until the loop has finished making one.

The name is the two halves

Diffusion is the method — how you generate. Transformer is the architecture doing the work. A DiT is just “we used a Transformer as the engine inside a diffusion model.” Stable Diffusion 1.x used a U-Net, a convolutional design; around 2023 Transformers were found to scale better, and every serious video model now is a DiT.

The trick

Teaching a network to draw a cat is hard. Teaching it to look at a slightly-noisy cat and guess which part is noise is much easier. Diffusion models only ever learn the easy task, then get the hard one by repeating it 20–50 times.

The network never draws anything. It only ever answers “which part of what I'm seeing is noise?” — that answer is subtracted, and the result is fed back in. One pass through that is one step. This is why there is no streaming: at step 10 of 20 you don't have half a video, you have a full-length video that still looks like fog.

Why a Transformer

Guessing the noise needs global context. To know whether this patch is noise you need to know what's happening in the rest of the frame — and in every other frame, because the cat's tail in frame 200 must belong to the same cat as the head in frame 1. Attention is exactly the mechanism that lets every position see every other position.

That requirement is your performance problem. It's the direct cause of the O(n²) cost that §07 measures at 70% of runtime.

Where the noise comes from — not from any model

The most common misconception

The starting noise is produced by a random number generator. That's it — torch.randn(shape, generator=seed). Pure Gaussian noise shaped like a compressed video. Nothing derives it from data, and no model generates it.

This is what a seed is: it picks which random canvas you start from. Same seed plus same prompt gives an identical video every time; changing only the seed gives a completely different take on the same prompt.

Qwen3-VL-32B does not produce it, and does not produce video. It converts your prompt into vectors, runs exactly once before the loop starts, and its output is then held constant for all 20 steps. Its language-model head is unused. It is an expensive prompt-to-vectors converter — expensive because prompt understanding is what decides whether “a cat knocking a glass off a table” produces the right sequence of events.

What a “token” is here

In Qwen a token is a word-piece. In a DiT it is a small patch of compressed video:

Comparable to a long LLM context — except every token attends to every other one, and the whole thing runs 20–50 times instead of once.

Inside one block — and why those tensor names look familiar

The network needs to know how noisy the input is right now: “remove noise from something 95% noisy” is a different job from “polish something 5% noisy.” Rather than feed that in as another token, a DiT injects it as a dial on every block — scale, shift and gate values that modulate the block's behaviour. That is AdaLN, Adaptive Layer Norm.

The property that matters: AdaLN depends only on the step number, never on your content. At step 7 all 91,728 tokens receive the same modulation values. That is precisely why 13 B of parameters can be collapsed into a lookup table — see §03.

Two ways to condition, and why they differ

Worth knowing because it decides which task mode you want:

Keyframes (fl2va) go through the video VAE
Your input image must be pixel-exact — frame 1 of the output is your image — so it is encoded into the same latent space as the output and dropped in as “keyframe conditioning latents.”
References (ref2va) go through Qwen3-VL's vision tower
These only need to convey identity or style, not exact pixels, so they ride the semantic encoder — and the diffusers docs note they are placed on the conditioner's 2 fps grid, a much coarser sampling than the 24 fps output.
The whole pipeline, in order
  1. Once, before the loop — Qwen3-VL encodes your prompt into vectors.
  2. Once, before the loop — randn(seed) creates the canvas.
  3. 20 times — the 50 DiT blocks read the whole sequence, predict the noise in the hot rows, subtract a little. This is 99% of your runtime.
  4. Once, after the loop — the VAEs decode latents into pixels and stereo audio.

Everything in the optimization ladder attacks line 3, and only in two ways: make each pass cheaper (SageAttention, Sol-Attn, fp8) or do fewer passes (turbo LoRA, caching).

06

How this differs from every Qwen you've deployed

You have vLLM, llama.cpp and 200 GB of Qwen checkpoints on this box already. Here is precisely which of those instincts transfer and which actively mislead.

The loop is inverted

An LLM does many cheap passes: one forward pass per token, each touching all weights but computing on a single new position. Generation length is discovered at runtime; the model stops when it emits EOS.

A diffusion model does few enormous passes: a fixed number of denoising steps decided before generation starts, each one a full bidirectional pass over the entire output at once. A “step” is a point on a scheduler's sigma grid, not a token. There is no EOS and no streaming — at 40% of the steps you don't have 40% of the video, you have a full-length video that still looks like noise.

The one intuition that transfers

Both read the whole weight set repeatedly. For an LLM that's per token; for a diffusion model it's per step. So “tokens/sec ≈ bandwidth ÷ model bytes” has a direct analogue — it's just that for video the analogue lands nowhere near the binding constraint, because each sweep does vastly more arithmetic. That's §07.

Attention is O(n²) in that number. Doubling your resolution quadruples the dominant cost. This is why the single most effective thing you can do on a slow box is generate smaller and upscale — and why §08 ranks the optimizations the way it does.

LoRA means something different too

You've probably seen LoRA used to teach an LLM a domain or a format. Here the highest-value LoRAs don't change what the model makes — they change how many steps it needs. A “turbo” LoRA is a distilled student that reaches the same place in 4–8 steps instead of 20–50. There is no real LLM equivalent; speculative decoding is the nearest cousin.

Correction — this reverses my own opening claim

Earlier in our session I told you bandwidth was your scarcest resource. That's true for the Qwen models on this box and false for this one, and since it changes which optimizations are worth your time, it's worth being exact about.

The roofline knee is 100 TFLOP/s ÷ 251 GB/s = 398 FLOP/byte. A workload above that line is compute-bound; below it, bandwidth-bound.

The H3 denoise step sits 110× past the knee. Its bandwidth floor for 14 steps is 3.7 s; the compute cost is ~624 s. Memory traffic is 0.6% of the problem. You are FLOPS-limited, not bandwidth-limited.

Two independent published results agree, and they're the kind of evidence that's hard to argue with — someone cut a video model's weights by 33% via NVFP4 on a Spark and generation got 6% slower (18.0 s → 19.1 s) Published. A 33% reduction in bytes producing no speedup is the diagnostic signature of a compute-bound kernel. Separately, torch.compile was reported to give “essentially 0% speedup on GB10.”

Practical gotchas specific to this box
  • nvidia-smi reports memory as “Not Supported” / N/A on GB10 Measured. Every “watch nvidia-smi for VRAM” instruction you'll read is inapplicable. Use free -g for capacity and nvidia-smi dmon for sm% / power / temp.
  • Your system python3 has torch 2.10.0+cpu — cuda.is_available() == False. Plain pip install torch on aarch64 silently resolves to a CPU wheel. Always --index-url https://download.pytorch.org/whl/cu130; cp312 aarch64 wheels exist through 2.13.0 Measured.
  • Run headless. Xorg + gnome-shell are holding 873 MiB of unified memory you'll want.
  • Swap is only 16 GiB; the vLLM path has been observed using 12.6 GiB of it.
08

The optimization ladder

Ranked by measured payoff on this hardware, not by how often they're mentioned online. The ranking is a direct consequence of §07: things that cut FLOPs win, things that cut bytes don't.

1

Cross-step caching biggest single lever

710.6 s → 181.3 s  ·  3.92× at 480p/50 steps Published

Adjacent denoising steps produce very similar hidden states, so you can skip recomputing transformer blocks and reuse a stale residual. TeaCache tracks the L1 distance between consecutive modulated inputs against a threshold (rel_l1_thresh 0.1–0.2); variants are EasyCache, FBCache, Cache-DiT, and H3FirstBlockCache.

NVIDIA's own Sol Engine measurements attribute the largest jump to this, and critically it needs no distillation, no LoRA, no calibration pass. It's approximate — unlike an LLM's KV cache, which is exact — so quality degrades if you push the threshold.

2

Turbo LoRA — step distillation what you asked about

20–30 steps → 4–8  ·  3–5×, linear in step count

Your link larryvrh/MiniMax-H3-Turbo-Lora is real: 606k downloads, Apache-2.0, rank 64 on attention/MLP and rank 16 on adaln_proj, 779.8 MB per file. The technique is DMD2 — adversarial distribution-matching distillation — confirmed by the author himself, not LCM and not CFG distillation.

An important correction to the usual framing: most turbo-LoRA writeups claim 6–10× because they assume you also drop CFG. H3 is already CFG-distilled, so there's no 2× to reclaim. The honest number is the step ratio alone, 3–5×.

Settings that work: strength 1.0, euler + simple, shift 6/3 at 768p. Note the off-by-one — num_inference_steps counts sigma grid points including the terminal zero, so an “8-step” adapter is requested as 9 and a “4-step” as 5. Quality cost is real: motion smear on fast motion at 4 steps, which the author acknowledges as unsolved. 6–8 is the sweet spot.

Alternatives worth knowing: lightx2v/Minimax-h3-Turbo (529k downloads, also DMD, from ModelTC) and Minimax-h3-Turbo-SLA, which bundles 85% attention sparsity into the same adapter.

3

Generate small, upscale after

6.03×  ·  875 s → 145 s Published

Falls directly out of the O(n²) math in §05. Rendering at 640×360 and upscaling 2× to 720p beat direct 720p by 6× in one published Spark benchmark. Unglamorous and the largest single win available to you. Choice of upscaler matters too — swapping Real-ESRGAN for SPAN cut another 282 s (22%) off a run. NVIDIA VSR is permanently unavailable on Spark, so don't plan around it.

4

Sol-Attn — sparse attention not what the name suggests

1.57× on its own Published

Your NVIDIA forum link advertises “SOL attn acceleration,” and it's worth clearing up what that is: not speed-of-light, not a SageAttention rebrand. Sol-Attn = Sparsifying Online attention, a training-free dynamic sparse-attention method from NVlabs (arXiv 2607.24027, July 2026), shipped on the sol-engine branch of NVlabs/Sana and packaged as ComfyUI nodes.

It attacks the 70–83% of your runtime that is attention by not computing all of it. On GB10 specifically the flex_attention path is numerically wrong (cos ≈ 0.92 vs SDPA) and the sm_121 patch forces the triton_ref kernel (cos ≈ 0.99998) — a detail that would be very hard to debug on your own.

5

SageAttention — quantized attention what you asked about

1263.5 s → 1010 s  ·  1.20× end-to-end on H3/GB10, 1.32× on the sampling stage alone Published

It's quantized attention, not sparse: Q·Kᵀ in INT8 with outlier smoothing, P·V in FP8 e4m3 with a two-level FP16→FP32 accumulator. My measurements say exactly why it helps here and by how much: your bf16 attention already runs at 93% of the matmul roof, so there is no kernel-engineering headroom left — but fp8 measured 195 TFLOP/s against bf16's 100. The ~2× precision headroom is the entire mechanism, and a 20% end-to-end gain is what that converts to once non-attention work is included.

Build reality on your box:

  • PyPI ships only 1.0.6 (the old Triton v1) Measured. You must build 2.2.0 from GitHub source — there is no aarch64 wheel anywhere, and the usual prebuilt-wheel mirror is Windows-only.
  • sm_121 is supported upstream: SUPPORTED_ARCHS includes "12.1" and maps it to compute_121a,code=sm_121a. Build with TORCH_CUDA_ARCH_LIST="12.1", ~10 min.
  • There is no dedicated sm_12x kernel — sm_121 compiles the Ada sm_89 sources retargeted. It works, but that's what you're running.
  • Needs TRITON_PTXAS_PATH=/usr/local/cuda/bin/ptxas and generally TORCHDYNAMO_DISABLE=1, because Triton's bundled ptxas can't do sm_121a.
  • SageAttention 3 is broken on GB10 — mosaic artifacts, TMA descriptor failures, and no faster than 2.2. Ignore anything advertising SA3 on sm_121a.
  • Open correctness bugs specifically with H3: the fp8 PV kernel silently emits pure noise above ~160k packed tokens. Your realistic shapes (~92k max) sit below that, but know the cliff exists.
6

Quantization capacity, not speed

~0× speed  ·  but it's the reason the model fits at all

This is where LLM instincts hurt most. On your Qwen models, NVFP4 is a genuine 1.5× — measured Qwen3-8B goes 25.65 → 38.6 tok/s, because decode is bandwidth-bound. On H3, NVFP4 cut weights 33% for −6% speed. Weight-only formats unpack to bf16 before the matmul, so the FLOPs are identical and the FLOPs are what you're short of.

Quantize anyway — you have no choice, since bf16 is 123.8 GiB against 121.7 GiB of RAM. Just book it as “makes it fit and loads faster,” not “makes it fast.”

One exception, and it's the one to take: fp8 is not weight-only on this box. Measured Measured _scaled_mm runs at 192.2 TFLOP/s against bf16's 92.8 — a genuine 2.07× on the compute you're actually short of. INT8 goes the other way at 0.63×. So the format choice is not “which is smallest” but “which has native tensor cores here,” and the answer is fp8. See §04.

7

Things not to bother with

zero or negative

  • CPU offload / --lowvram. Every guide written for a 24 GB 4090 recommends it. Here host RAM is VRAM, so it buys zero capacity and costs a 55 GiB/s memcpy Measured. vLLM's own GB10 notes call DLO “actively harmful” — OOM-killed with exit −9.
  • torch.compile. Reported ~0% on GB10. The 3× someone did get came from PTX→SASS kernel caching, which is a first-run cost, not compilation.
  • FlashAttention 2/3/4. No sm_121 kernels. FA2 builds but matches or loses to SDPA; FA3 is Hopper-only; FA4 needs tcgen05/TMEM that sm_121 lacks. flash-attn is sdist-only on PyPI anyway Measured — no wheels for any platform.
  • Pinned memory. Measured identical to pageable Measured. It's a coherent pool; there's no DMA to optimize.
  • A second Spark. ConnectX at 200 Gb ≈ 24.5 GB/s is ~1/10 of one Spark's own memory bandwidth. Not the first move.
09

What ComfyUI is, and why this world uses it

You asked what it is and how it relates to the model. The short version: it is not a server for a model, and that's exactly the point.

ComfyUI is a DAG interpreter whose node outputs are live PyTorch objects — MODEL, CLIP, VAE, CONDITIONING, LATENT, IMAGE. A “workflow” is JSON of the form {node_id: {class_type, inputs}}, where an input is either a literal or a [source_node, output_slot] edge. The backend topologically sorts it, caches per-node results, and executes.

The thing that surprises people coming from vLLM

The denoising loop is not in the graph. Loaders produce objects, text encoders produce conditioning, and then a single KSampler node runs all N steps internally and emits one latent. VAEDecode turns that into pixels.

So the graph is pipeline assembly — the part vLLM hardcodes — not the inner loop. That's the whole design thesis.

Why a graph instead of an endpoint

Image and video generation has no stable request schema. Every result is a different composition: LoRA stacks, ControlNet, IP-Adapter, multi-stage sampling, latent upscale, refiner passes, frame interpolation, per-node device placement. A stateless /v1/videos endpoint would need a new parameter for every one of those. A graph makes composition be the interface.

ComfyUI is also aggressively stateful about weights — models persist across requests and stay partially resident — which is precisely what a stateless server is designed to avoid. On a 5-model pipeline where the text encoder alone is 62 GiB, that statefulness is the difference between a 9-minute cold start and an instant second run.

How it relates to H3 specifically

ComfyUI has official H3 support with documented workflows. Its model layout is models/diffusion_models, models/text_encoders, models/vae, models/loras — and note it usually wants repackaged single-file weights, not the diffusers folder tree. That's why Comfy-Org publishes repacks, and why grabbing the right subset is 39.6 GiB rather than the 464 GiB a naive full clone would pull — see why the two stacks differ.

It's also the only path where the whole §08 ladder composes: turbo LoRA + Sol-Attn + SageAttention + FirstBlockCache stack as nodes in one graph. vLLM-Omni supports none of the LoRA half.

Honest downsides

  • Supply chain. Custom nodes are arbitrary Python from GitHub, auto-loaded at startup. Community H3 forks bundle up to 14 packs.
  • Reproducibility. A workflow JSON pins node names, not node versions. Version drift silently changes output.
  • pip can destroy your build. Installing sageattention or onnxruntime from PyPI will happily overwrite your locally compiled sm_121 wheel with one that doesn't work.

What I could not settle

Stated plainly rather than papered over, because each one is cheap to resolve empirically and expensive to guess wrong.

  • No one has published a MiniMax-H3 wall-clock for the vLLM path at a full-size shape on Spark. vLLM's own GB10 section declines to give one, saying only that it is “far higher” than the multi-GPU profiles. My §07 model predicts it; nobody has measured it.

  • Pruned vs unpruned, and int8 vs fp8 vs bf16 quality — all unmeasured.   • Whether int8_convrot actually works on sm_121 in ComfyUI. Comfy-Org recommends it for cu130 users and one practitioner reports using it on a Spark, but I found no first-hand success log with timings.
  • SageAttention 2.2.0 is built but not runtime-tested on this box. Version 1.0.6 was measured here: 1.09× at S=16,384 and 1.14× at S=46,410, cosine similarity > 0.9999 versus SDPA. A 2.2.0 ARM64 wheel then built for sm_121a and was not installed before the session ended.

What has been chosen, why, what was rejected, and specifically what evidence would reverse it. Provisional entries are decisions taken to unblock work, not conclusions.

D-01

ComfyUI, not vLLM-Omni, for the first deployment

adopted
Why
4× smaller download, 41 GiB resident vs 105 GiB, supports the turbo LoRA and the whole optimization ladder, and leaves ~49 GiB to experiment in.
Rejected

Reverses if

D-02

provisional
Why

Rejected

D-03

Generate at 1312×736, upscale to 1080p

superseded by D-05

Chosen on the reasoning “take the largest canvas that upscales uniformly.” Two pieces of evidence killed it: native high-res sampling is measurably slower than generating small and upscaling, and audio corruption at ~1 MP with few steps is a documented failure mode. Kept on record because the reasoning was wrong in an instructive way — it optimised the scale factor when the scale factor was not the constraint.

D-04

SPAN as the upscaler

adopted
Why
Measured on Spark over 362 frames to 1080p: SPAN 49.2 s vs Real-ESRGAN 316.0 s — 6.4× faster. It is also a PSNR-oriented regression network rather than a GAN, so it hallucinates less per-frame detail and should flicker less on video, not more. And it is stock spandrel in ComfyUI — zero custom wheels, which matters enormously on aarch64. The model file is 4.3 MB.
Rejected
Real-ESRGAN — 6.4× the cost, GAN-based so more temporal shimmer. NVIDIA VSR — permanently unavailable: nvidia-vfx is x86_64-only wheel-stubs, and NVIDIA staff stated on 2026-04-01 “There is currently no plan to add NVIDIA VFX support on Spark.” (It does the same 362 frames in 11.2 s on a 5090 — the single biggest structural gap versus x86.) SeedVR2 — 6–20× more expensive again.
Upgrade path
FlashVSR if per-frame flicker turns out to be visible — one-step streaming diffusion VSR with genuine cross-frame propagation, est. 150–250 s on Spark, and the 1038lab wrapper needs no custom CUDA kernels.
Free lever not yet taken
RIFE frame interpolation: 24→48 fps at constant duration for an estimated 15–30 s, ~3% of the run. A/V-safe as long as duration is held fixed. Caveat: its ComfyUI node depends on cupy, an aarch64 pain point, with a taichi backend as fallback.
D-05

Generate at 960×544, 2× SPAN to 1080p

provisional — replaces D-03
The inversion
Same author, same seed, 20 steps, ~5 s clip: native 1344×768 = 637 s vs 960×540 + 2× upscale = 349.9 s. Upscaling is 1.82× faster and produces a larger frame. Generating big is not a quality option you pay for — it is strictly dominated. D-03 optimised the wrong variable.
Why 960×544
Exactly 2.00× to 1920×1088 (crop 8 rows to 1080) — the cleanest possible scale factor. 0.52 MP, which is the region where audio survives few-step sampling. And it is the exact shape of the only measured Spark 1080p run: 741 s for a 15.08 s clip with joint audio.
Rejected
1312×736 / 1344×768 — slower and in the audio-corruption zone. 1024×576 — fine alternative, 1.88× scale, ~8% more sampling cost.
Reverses if
Output is visibly soft after 2× upscaling → step up to 1216×672 (1.58×) and accept ~40% more sampling time. Flicker is visible → D-04's FlashVSR path.
Note
The published run states 960×540, but 540 is not a multiple of 32 — diffusers would reject it. Either the blog rounds or the ComfyUI path pads. 960×544 is the legal neighbour; use that.
D-06

Audio governs the step count, not video

provisional
Finding
The risk flagged as unmeasured at the start of this briefing is now documented. Community reports: “at 1 MP resolution and 4 steps, the audio still gets corrupted”; and duration-dependent — “5 seconds can usually work… try 10 seconds, or even 15… the audio is nearly always unusable.” ComfyUI's own docs describe turbo mode as “slightly lower audio and motion quality.” The clearest careful report: 4-step audio is coherent but below a 20-step generation; 8 steps is cleaner.
Confound to know
Most severe pre-2026-08-07 “turbo destroys audio” reports were a ComfyUI sampler bug, not the LoRA — H3 runs video and audio on two different flow schedules, and stock single-clock Euler integrated them on one clock. Fixed 2026-08-06 in commit bdcb886a (ModelSamplingAV). Use a ComfyUI newer than that and discount every older report.
Decision
8 steps, not 4, for anything with dialogue. 4 steps only for silent clips or fast seed-hunting. Resolution and step count are the clearer audio risks. Duration alone has not been isolated as a cause of unusable audio — see D-07.
Also
In a controlled 1 MP / 15 s / 4-step comparison of four turbo LoRAs, the 50-step baseline was still judged best overall. Turbo is a real quality trade, not a free lunch.
D-07

adopted
Why

Duration was not isolated as an audio-quality cause, so there is no need to stay at 5.17 s once the pipeline works.
Rejected

Smoke test

Reverses if

Reading the diffusers source disproves that: canvas_max_pixels is consumed only inside resolve_canvas_size, which runs only when height and width are omitted. Grep the whole module and no code path ever compares height × width against it. It is a soft default for deriving a canvas from an aspect ratio — pass explicit dimensions and it is bypassed entirely.

What actually makes 1920×1080 a hard error is the granularity rule: 1080 ÷ 32 = 33.75. 1920×1088 would pass every check diffusers performs and simply run. The real barriers to native 1080p are that H3-Base is trained at a 768 px short edge — a user at 1376×768 (2.4% over the nominal cap) reported “distorted faces and heavy artifacts” — and that H3-Regenerate-2K is hosted-API-only, stated verbatim in MiniMax's README as “not yet open-sourced.”

The practical conclusion is unchanged, and D-05 now rests on a stronger reason anyway: generating small and upscaling is faster, so the ceiling never binds.

Two corrections to earlier guidance in this briefing
  • Shift does not track resolution. I speculated it might need to be 6/3 at high res. It doesn't — shift tracks distillation. LightX2V's non-distilled base config at 1344×768/362 frames uses 12.0, identical to its 544p base configs, while its 544p DMD 4-step config uses 6.0. Use 6/3 with the turbo LoRA at any resolution; 12/3 without one.
  • The 768p turbo adapter is not the high-res answer. A discussion thread titled “768p way worse than 544p” reports the 768p v1.0 giving oversaturation, bad audio and poor prompt adherence; several users find the 544p-trained v0.1 better even above 1 MP. A v1.1 768p adapter released 2026-08-20 is widely reported better than v1.0 and is missing from the vendor's own spec table — that is the one to try, at LoRA strength 1.2–1.3 near 1 MP rather than 1.0.
